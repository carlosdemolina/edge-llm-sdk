# edge-sdk

Prototype of an embedded (in-vehicle) LLM assistant built on a Zero Trust
architecture: two parallel HTTP pipelines — a **secure** one (ingress
sanitization, DSL whitelist, contextual policies, canary tokens, etc.) and a
**vulnerable** one (almost no controls) — designed to compare and quantify
the effect of each security control side by side. See
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the full pipeline design.

This document covers only **usage**: how to start the server manually and
how to run the automated test/calibration/red-team suite.

## Requirements

- Python 3.13 and a virtual environment with `pip install -r requirements.txt`.
- [Ollama](https://ollama.com) running locally, with the models you intend
  to use already pulled, e.g.:
  ```bash
  ollama pull llama3.2:1b
  ollama pull llama3.2:latest
  ```
- A `.env` file at the project root with, at minimum:
  ```
  AUDIT_LOG_HMAC_SECRET=<32-byte hex>
  SDK_TOKEN=<token for protected routes>
  OLLAMA_HOST=http://localhost:11434
  OLLAMA_MODEL=llama3.2:latest
  ```
  (`OLLAMA_MODEL` is the default value; the test suite overrides it per
  process to compare several models without touching `.env`.)

## Starting the server manually

```bash
source venv/bin/activate
uvicorn app.server.main:app --reload
```

By default this serves `http://127.0.0.1:8000` (the static dashboard is
included). To enable the debug panel (full per-request traces in
`logs/debug_trace.jsonl` and via `GET /api/debug/traces`):

```bash
SDK_DEBUG_MODE=true uvicorn app.server.main:app --reload
```

## Cleaning generated outputs

`scripts/clean.sh` **destructively** removes (no backup) everything
generated by tests and manual runs:

- `logs/*.log`, `logs/*.jsonl` (keeps `.gitkeep` and any
  `debug_trace_baseline_*.jsonl`, which are manually captured reference
  snapshots).
- Everything under `redteam/reports/`.
- `__pycache__/` and `.pytest_cache/` caches across the repo.

```bash
./scripts/clean.sh          # asks for confirmation
./scripts/clean.sh -y       # no confirmation
```

## Running the full suite (tests + calibration + red-team, multi-model)

`scripts/run_suite.sh` (a wrapper around `python -m redteam.run_suite`)
automates the full cross-model comparison process:

```bash
./scripts/run_suite.sh                                    # default models
./scripts/run_suite.sh --models llama3.2:1b               # a single model
./scripts/run_suite.sh --models llama3.2:1b llama3.2:latest
./scripts/run_suite.sh --skip-pytest                       # calibration + red-team only
./scripts/run_suite.sh --kill-stale-server                 # kill a stray uvicorn on :8000, if any
```

`--kill-stale-server` only stops a process if its command line matches
`uvicorn app.server.main:app` (e.g. a manual `uvicorn --reload` you forgot
to stop, or a previous suite run that didn't shut down cleanly). If port
8000 is held by any other process, the suite aborts without touching it.

For each model given (default `llama3.2:1b` and `llama3.2:latest`, in that
order), the suite:

1. Runs `redteam/calibrate_prompt.py` in-process (no HTTP server) against
   `redteam/calibration_prompts.json` — prompt quality/semantics, always
   against the secure pipeline.
2. Starts a real `uvicorn` server with `SDK_DEBUG_MODE=true` and
   `OLLAMA_MODEL` set to that model, and waits for `GET /api/state` to
   respond.
3. Runs `redteam/run_redteam.py` against that server — the attack catalog
   (`redteam/attack_prompts.json`) against both pipelines (secure/
   vulnerable) over HTTP.
4. Stops the server and archives that model's results (including
   `logs/debug_trace.jsonl` and `logs/calibration_audit.log`) before moving
   to the next model, leaving those two logs empty for it.

Before the per-model loop, `tests/` runs once (unit tests are
model-independent, so there is no point repeating them).

### Report layout

`pytest` results are only shown on the console (no separate report file);
everything else lives under `redteam/reports/<run_id>/`:

```
redteam/reports/<run_id>/
├── comparison.json          # aggregated comparison, all models
├── comparison.md            # same comparison as a Markdown table
├── llama3.2-1b/
│   ├── calibration.json
│   ├── redteam.json
│   ├── debug_trace.jsonl
│   └── calibration_audit.log
└── llama3.2-latest/
    ├── calibration.json
    ├── redteam.json
    ├── debug_trace.jsonl
    └── calibration_audit.log
```

`<run_id>` is a UTC timestamp (`YYYYMMDDTHHMMSSZ`).

### Reading `comparison.md`

One row per model, with:

- **Calibration**: `PASS/FAIL/REVIEW` from the calibration catalog (secure
  pipeline only).
- **Red-team (secure)** / **Red-team (vulnerable)**: `PASS/FAIL/REVIEW` from
  the attack catalog, for each of the two pipelines.
- **Avg latency (ms)**: average `sdk_total_duration_ms` across every traced
  request for that model (calibration + red-team combined).
- **Traced requests**: number of requests behind that average (requests
  blocked before ever calling the LLM still count, since they still
  produce a trace).

`PASS`/`FAIL`/`REVIEW` follow the same criteria in calibration and red-team
(see `redteam/scoring.py`): `FAIL` means an explicitly forbidden outcome was
reached, or the result doesn't match the expected verdict/action; `REVIEW`
means the catalog entry has no automatic expectation and requires manual
inspection of the JSON report.
